## 1. Executive summary

FastTrack Social Funnel is a Windows-local workspace for planning, reviewing, packaging, scheduling, and safely publishing a 30-day social campaign in Turkish, English, and Brazilian Portuguese across Instagram, Facebook, TikTok, and Threads.

The social account setup and profile-branding phase is effectively complete. The repository already contains a working local application skeleton, 30 campaign ideas, 90 localized content units, 360 destination jobs, SQLite persistence, a review dashboard, static/carousel rendering, a minimal video renderer, ZIP export, publisher adapter foundations, credential-vault support, backup/restore, Windows packaging, and tests.

The most important new decision is:

- **Do not build an automatic Reels/video creator.**
- The user will produce Reels/TikTok videos manually outside the application, currently using Claude Motion Designer, then upload them into the Windows EXE.
- The application must accept a complete monthly media upload, validate it, map files to campaign slots, and use those exact supplied videos for scheduled publishing.
- The assistant is responsible for producing the non-video campaign media: single-image posts, carousel slides, captions, calls to action, hashtags, and health disclaimers.
- **The user is not taking over publishing.** After the user uploads the videos, the application/assistant remains responsible for review, scheduling, and publishing to the connected social accounts.
- Official platform APIs are the intended production path. Daily ZIP export remains a backup, audit, and emergency manual-delivery path rather than the primary workflow.

Do not resume the superseded Reels renderer design in `docs/superpowers/specs/2026-10-22-reels-renderer-design.md`.

## 6. Approved monthly media import direction

The user approved a monthly upload workflow inside the packaged EXE. The recommended first implementation is a ZIP importer plus per-slot replacement in the local dashboard. Imported assets feed the scheduler/publishers; they are not merely exported back to the user.

### Proposed ZIP layout

Use normalized paths so files can be mapped without guessing:

```text
fasttrack-YYYY-MM/
  media-manifest.json
  day-01/
    tr/video.mp4
    en/video.mp4
    pt-BR/video.mp4
  day-02/
    tr/slide-01.png
    tr/slide-02.png
    tr/slide-03.png
    en/slide-01.png
    ...
  day-04/
    tr/post.png
    en/post.png
    pt-BR/post.png
```

The importer should accept the directory prefix or files directly at the ZIP root. Normalize internally.

### Import responsibilities

1. Reject unsafe archive paths (`..`, absolute paths, drive prefixes, symlink-like entries).
2. Extract to a temporary staging directory, never directly over active media.
3. Validate supported extensions and actual file formats.
4. Validate day range, locale, expected slot, file count, and duplicate paths.
5. Validate PNG dimensions with Pillow.
6. Validate video codec, dimensions, duration, and stream presence with `ffprobe`.
7. Calculate SHA-256 checksums.
8. Show a preflight report before activation: complete, missing, invalid, duplicate, and unexpected slots.
9. Activate atomically only after validation succeeds and the user confirms the import.
10. Preserve the previously active package so rollback is possible.
11. Store media metadata in SQLite; never store media blobs in SQLite.
12. Allow one slot to be replaced later without reimporting the whole month.

### Recommended storage model

Add an imported-media binding keyed by campaign, content revision, day, locale, and logical slot. A practical shape is:

```text
campaign_slug
content_revision
day
locale
kind            # video | image | carousel_slide
position        # 0 for image/video; 1..N for carousel
source_path
managed_path
checksum
width
height
duration_ms
mime_type
import_batch_id
created_at
```

Store imported files beneath the user workspace, for example:

```text
%LOCALAPPDATA%\FastTrack Social Funnel\media\imports\<batch-id>\...
```

The active binding should point to one immutable imported file. Replacement creates a new record/file and switches the binding; it should not overwrite the old file in place.

### Dashboard behavior

Add:

- `Aylık medya yükle` action.
- Drag/drop or file-picker ZIP upload.
- A 30-day × 3-locale coverage matrix.
- Clear statuses: ready, missing, invalid, replacement available.
- Validation details without secrets or raw internal traces.
- Per-day preview.
- Per-slot replace action.
- Import history and rollback to the immediately previous active batch.

Do not mix OAuth/live-network work into the first media-import increment. First make import, validation, persistence, preview, media resolution, and ZIP fallback correct; then wire the same resolved assets into the existing publishers in the following increment.

### Media resolution order

For a job that requires media:

1. Use an explicitly imported active media binding.
2. For image/carousel slots only, allow the reviewed assistant-produced deterministic asset if no imported replacement exists.
3. For video slots, fail closed with `missing_media`; never fall back to the current three-second generated video.
4. Threads may remain text-only.

After resolution and validation, approved jobs flow to the scheduler and official platform publisher. ZIP export uses the identical resolved files as a fallback and audit artifact.

## 14. Security and operational constraints

- Never put credentials in source, logs, screenshots, ZIP manifests, database rows, or chat output.
- Keep `.env` files out of Git; `.env.example` may contain names only, never values.
- Keep OAuth tokens in Windows Credential Manager or an encrypted equivalent.
- Redact tokens and authorization headers from errors.
- Do not solve CAPTCHAs or bypass security interstitials.
- Do not save passwords in the browser.
- Do not enable Instagram Inbox access through Facebook without explicit request.
- Do not disconnect social accounts or portfolios.
- Do not delete old posts/accounts.
- Do not use browser clicking as the production publishing mechanism. Use official APIs. Browser operation is limited to account setup, recovery, or an explicitly requested one-off fallback.
- Treat ZIP export as backup/audit/emergency delivery, not as an instruction for the user to publish everything manually.
- Require explicit user approval before activating a public campaign batch or a one-off test post. Once a reviewed batch is activated, its scheduler may publish the approved jobs at their configured times.
- Preserve fail-closed behavior when a remote publication outcome is unknown.
- Do not retry blindly when a remote ID may already exist.
- Validate imported ZIPs against archive traversal and decompression abuse before extraction.
